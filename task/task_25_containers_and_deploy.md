## Цель

Получить проверяемый единый deploy новой версии с фиксированными артефактами, постоянными данными и готовностью в LAN.

## Ожидаемый результат

Обновлённые Dockerfile/Compose/entrypoint/local PB scripts, новый `scripts/deploy.sh`, `.env.example` и протокол `task/deploy_qa.md`.

## Объём работ

1. Реализовать runtime_contract: фиксированные версии/артефакты, проверка PB 0.40.1 и архитектуры, воспроизводимая Web+Shelf сборка, отдельное PB-хранилище.
2. Создать безопасный .env.example со всеми применяемыми переменными и placeholder, согласовать CORS/session transport/NO_PROXY; секреты не выводить и не передавать в Web build.
3. Реализовать deploy preflight, bounded ожидание PB и Shelf health, ненулевой exit при отказе. build.sh оставить коротким документированным wrapper либо удалить с заменой всех ссылок.
4. Обеспечить persistent volume новой версии, повторный запуск/обновление без потери данных; запуск схемы и service-account bootstrap не должен скрыто менять путь базы.
5. Добавить явный ограниченный режим очистки только dev-базы по runtime contract: проверка canonical path/именованного тестового тома, отказ для /, пустого, родительского/неизвестного пути; default никогда не очищает данные.
6. Проверить статическую раздачу и прямые Web-ссылки с reload, запуск с HOST=0.0.0.0, доступ со второго LAN-устройства и недоступность PB оттуда. Реальный адрес не придумывать.
7. Проверить первый запуск, повторный запуск с сохранённым новым отчётом, остановку/логи, ошибки конфигурации и health. Использовать изолированный проект/том; рабочие контейнеры владельца не пересоздавать для QA. Реализовать согласованный `--self-test`, автоматически выполняющий эти проверки на собственных временных ресурсах.

## Что не входит в задачу

Автоматический удалённый CD, миграция старых данных, неизвестные адреса/аккаунты, запуск разрушительных проверок на рабочем томе.

Общие исключения продукта: комментарии/история, экспорт/печать, массовое подтверждение, клиентская админка и офлайн-синхронизация.

## Функциональные требования

- По `scripts/deploy.sh --help` и .env.example можно воспроизводимо поднять два контейнера; успех сообщается только после health API+PB.
- Повторный deploy сохраняет записи новой версии, unsafe reset отклоняется, путь persistent data однозначен.

Обязательные подробности поведения перечислены в объёме работ. Поля и DTO брать из зафиксированных контрактов.

## Ошибки и особые случаи

- Неверный секрет, отсутствующий PB, неподдерживаемая архитектура/движок, занятый порт, прокси и timeout.
- Повторный старт и обновление, падение одного контейнера, прерванный reset, deep link reload.

## Автоматические проверки

Все команды выполняются из корня репозитория. Окружение должно соответствовать согласованным версиям; тесты работают только на временных базах. `scripts/check.sh` создаётся в Task 22, после Task 23 полный запуск включает E2E; `scripts/deploy.sh` и его изолированный `--self-test` создаются в Task 25. Это целевые команды зависимостей, а не существовавшие при аудите файлы.

```bash
bash -n scripts/deploy.sh
sh -n entrypoint.sh
bash scripts/check.sh
bash scripts/deploy.sh --help
bash scripts/deploy.sh --self-test
git diff --check
```

Если команда или путь изменены выполненной зависимостью, сначала зафиксировать актуальную замену и причину, затем выполнить её. Ошибка окружения и пропуск обязательной проверки не означают успешную приёмку.

## Ручная проверка

На подготовленном изолированном стенде выполнить первый и повторный deploy, сохранить отчёт между запусками, проверить со второго LAN-компьютера; при отсутствии второго устройства не отмечать этот пункт пройденным.

Ожидаемый результат — критерии приёмки выше. Записать фактическую среду, шаги и наблюдения; ручную проверку не подменять наличием теста.
