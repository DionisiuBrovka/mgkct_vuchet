## Цель

Реализовать чистую схему по data_schema.md и доказать её ограничения на временных экземплярах PB 0.40.1.

## Ожидаемый результат

Новая исходная миграция, актуальные схемные тесты и изолированные фикстуры вместо исторической цепочки переноса.

## Объём работ

1. Заменить исторические миграции чистой воспроизводимой инициализацией строго по Task 05; пользователя, схему сессий и точные часы включить в полном объёме.
2. Реализовать subjects/groups, нормализованную уникальность, assignments и связи/индексы отчёта. Если нужны hooks целостности при записи через PB admin, держать их отдельно от бизнес-переходов Shelf.
3. Убрать display_name, user_profiles, статусы/подтверждение в строках и текстовые subject/group назначений; substitutions.description остаётся свободным текстом.
4. Заменить исторические тесты проверками чистого запуска, повторного migrate up, обязательных полей, уникальностей, удалений и отсутствия прямого доступа.
5. Согласовать серверные фикстуры с новой схемой в минимальном объёме. Если старый API временно несовместим, не добавлять legacy-поля: следовать порядку переключения Task 01 и явно пометить переходное состояние.
6. Не запускать run.sh на рабочем PB_DATA_DIR и не удалять локальную базу; фактический сброс выполняется только документированным явным режимом будущей Task 25.

## Что не входит в задачу

Перенос/архив старой базы, API и UI, транзакционная команда записи Task 10.

Общие исключения продукта: комментарии/история, экспорт/печать, массовое подтверждение, клиентская админка и офлайн-синхронизация.

## Затрагиваемые компоненты и файлы

- `data/pocketbase/pb_migrations/` — заменить исходную цепочку.
- `data/pocketbase/tests/` — заменить тесты переноса тестами новой схемы.
- `data/pocketbase/pb_hooks/` — при необходимости создать отдельный hook целостности.
- `server/test/` — только адаптация общей фикстуры, если этого требует согласованный переход.

Пути исходного аудита могут уточняться по результатам зависимостей. Новый путь не считать существующим до проверки; расширение объёма обосновать.

## Функциональные требования

- На двух независимых пустых базах создаётся одна и та же схема, повторный migrate up не меняет записи.
- Дубликаты справочников/назначений/периодов/строк и недействительные связи отклоняются хранилищем; правила удаления соответствуют контракту.

Обязательные подробности поведения перечислены в объёме работ. Поля и DTO брать из зафиксированных контрактов.

## Архитектурные ограничения

- Сохранять согласованность с результатами зависимостей и приоритетом product_spec.
- Не добавлять совместимость со старой базой/API и функции вне §20.
- Добавлять содержательные комментарии только к неочевидной логике.
- Клиент обращается только к Shelf и не знает коллекций PocketBase.
- Окончательные права, валидация, статусы и итоги принадлежат Shelf; PB обеспечивает ограничения и атомарность.
- Тестовые базы и учётные записи изолированы от рабочих данных.

## Ошибки и особые случаи

- Нормализация при создании и переименовании через админку; ссылочные удаления; нулевые часы как значение, не отсутствие required.
- Ошибка миграции не оставляет частичную схему; тесты не применяются к рабочей базе.

## Автоматические проверки

Все команды выполняются из корня репозитория. Окружение должно соответствовать согласованным версиям; тесты работают только на временных базах.

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s data/pocketbase/tests -v
git diff --check
```

При адаптации серверной фикстуры дополнительно выполнить `(cd server && dart analyze)` и относящиеся к ней тесты по согласованному переходу; не скрывать несовместимость старого API.

Если команда или путь изменены выполненной зависимостью, сначала зафиксировать актуальную замену и причину, затем выполнить её. Ошибка окружения и пропуск обязательной проверки не означают успешную приёмку.

## Ручная проверка

В изолированной PB-админке создать пользователя с одним name, предмет, группу и назначение; дубликат и удаление используемой ссылки должны давать предусмотренный результат.

Ожидаемый результат — критерии приёмки выше. Записать фактическую среду, шаги и наблюдения; ручную проверку не подменять наличием теста.
