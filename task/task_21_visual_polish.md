## Цель

Обеспечить единый русский интерфейс в голубой палитре с облаками и подтвердить удобство реальными браузерными проверками.

## Ожидаемый результат

Визуальные исправления, актуальные Web metadata и протокол браузерного QA `task/visual_qa.md` с размерами и наблюдениями.

## Объём работ

1. Сохранить существующую палитру и облака, выровнять AppBar, карточки, отступы, кнопки, статусные подсказки и feedback четырёх ключевых экранов.
2. Проверить понятность следующего действия на login/months/fill/review, пояснения сокращений и tooltips, состояния успеха/ошибки/пустоты, недоступные действия.
3. Проверить 360×800, 768×1024, 1366×768 как явное техническое допущение целевых размеров; дополнительно text scale 1.5 и клавиатурную навигацию. Уточнить размеры при известных устройствах колледжа.
4. Исправить overflow при длинных ФИО, предметах, описаниях и длинных точных числах; на узком экране часы удобно размещаются в несколько рядов, действия не перекрывают данные.
5. Проверить русский date control/locale и metadata Web, не создавать новый бренд или зависимость от нативных платформ.
6. Запустить приложение в браузере на release-артефакте, зафиксировать воспроизводимые шаги и скриншоты/пути в QA-протоколе; неисследованные размеры не отмечать как пройденные.

## Что не входит в задачу

Полная смена дизайна, новые функции и бизнес-правила, формальные golden-тесты каждой мелкой правки.

Общие исключения продукта: комментарии/история, экспорт/печать, массовое подтверждение, клиентская админка и офлайн-синхронизация.

## Автоматические проверки

Все команды выполняются из корня репозитория. Окружение должно соответствовать согласованным версиям; тесты работают только на временных базах. После изменения Freezed-моделей до тестов выполнить `(cd client && dart run build_runner build --delete-conflicting-outputs)` и проверить generated diff.

```bash
(cd client && flutter analyze)
(cd client && flutter test)
(cd client && flutter build web --release)
git diff --check
```

Если команда или путь изменены выполненной зависимостью, сначала зафиксировать актуальную замену и причину, затем выполнить её. Ошибка окружения и пропуск обязательной проверки не означают успешную приёмку.
