## Цель

Обеспечить автоматические проверки и проверяемые артефакты на согласованной CI-платформе тем же мастер-скриптом.

## Ожидаемый результат

Новая CI-конфигурация выбранной платформы, fixed tool setup/cache, публикация проверенных build artifacts и протокол CI.

## Объём работ

1. Использовать GitHub Actions по runtime_contract: при аудите host remote.origin.url — github.com. Перепроверить remote и доступность Actions перед созданием workflow; при запрете Actions зафиксировать реальный инфраструктурный блокер, не выдумывать runner.
2. Установить зафиксированные SDK/PB/browser/test dependencies; cache key учитывает версии и lockfiles, успешный cache miss не требует ручного состояния.
3. Вызывать `bash scripts/check.sh` со всеми обязательными стадиями включая E2E; не поддерживать второй расходящийся список проверок внутри CI.
4. Подготовить серверный binary, release Web и согласованные контейнерные/build артефакты с идентификатором commit/version и контрольными суммами; не публиковать секреты, тестовые пароли как production-config или PB-базу.
5. Проверить error propagation, timeout и cleanup; remote CD не настраивать, ручной deploy остаётся отдельным входом.
6. Выполнить локальную проверку конфигурации и доступный CI-run; отсутствие доступа к runner отмечать как непроверенное, не как зелёную сборку.

## Что не входит в задачу

Автоматический remote deployment, выдуманные runners/credentials, обход обязательных стадий.

Общие исключения продукта: комментарии/история, экспорт/печать, массовое подтверждение, клиентская админка и офлайн-синхронизация.

## Затрагиваемые компоненты и файлы

- `.github/workflows/check.yml` — создать для GitHub Actions по Task 08 (убедиться, что путь ещё не занят).
- `scripts/check.sh`, runtime/deploy tooling — только необходимые CI-совместимые исправления.
- `task/ci_qa.md` — создать протокол и ссылку на реальный run при доступности.

Пути исходного аудита могут уточняться по результатам зависимостей. Новый путь не считать существующим до проверки; расширение объёма обосновать.

## Функциональные требования

- CI на чистом runner проходит тот же master-check, что локально; намеренный тестовый отказ даёт failed job.
- Артефакты привязаны к commit/tool versions, пригодны документированному ручному деплою и не содержат секретов/баз.

Обязательные подробности поведения перечислены в объёме работ. Поля и DTO брать из зафиксированных контрактов.

## Архитектурные ограничения

- Сохранять согласованность с результатами зависимостей и приоритетом product_spec.
- Не добавлять совместимость со старой базой/API и функции вне §20.
- Добавлять содержательные комментарии только к неочевидной логике.
- Не раскрывать секреты и не удалять данные неявно; тестовый reset ограничен собственными ресурсами.
- Web — основная платформа; не изобретать удалённый CD или неизвестную инфраструктуру.

## Порядок выполнения

1. Проверить условия начала, результаты зависимостей и фактический код/документы из доказательств.
2. Подготовить воспроизводимый сценарий проверки, соразмерный риску задачи.
3. Выполнить пункты объёма работ в указанном порядке, не реализуя соседние задачи.
4. Проверить основной и негативные сценарии, выполнить команды и ручной QA.
5. Проверить diff, очистить собственные временные артефакты и обновить результаты/статусы.

Исполнитель вправе уточнить инженерный порядок в рамках требований; значимое отклонение объяснить в результате.

## Ошибки и особые случаи

- Пустой cache, отсутствие browser dependencies, падение E2E, недоступный artifact source.
- Pull request без секретов, несовпадающий lockfile и версия SDK.

## Критерии приёмки

- [ ] Артефакты привязаны к commit/tool versions, пригодны документированному ручному деплою и не содержат секретов/баз.
- [ ] Нет выдуманного удалённого CD, зависимостей от домашнего SDK или неописанного ручного cache.

## Автоматические проверки

Все команды выполняются из корня репозитория. Окружение должно соответствовать согласованным версиям; тесты работают только на временных базах. `scripts/check.sh` создаётся в Task 22, после Task 23 полный запуск включает E2E; `scripts/deploy.sh` и его изолированный `--self-test` создаются в Task 25. Это целевые команды зависимостей, а не существовавшие при аудите файлы.

```bash
bash scripts/check.sh
git diff --check
```

Если команда или путь изменены выполненной зависимостью, сначала зафиксировать актуальную замену и причину, затем выполнить её. Ошибка окружения и пропуск обязательной проверки не означают успешную приёмку.

## Ручная проверка

Открыть результат реального pipeline, проверить полную сводку и скачать/сверить артефакты; если runner недоступен — зафиксировать точный недостающий доступ.

Ожидаемый результат — критерии приёмки выше. Записать фактическую среду, шаги и наблюдения; ручную проверку не подменять наличием теста.

## Документация и очистка

Корневые документы окончательно сводит Task 27, но изменённые команды уже сейчас записать в результате задачи. Удалить собственные временные файлы/стенды, не чужие правки и не рабочие данные. Зафиксировать доказанные отклонения для ещё не начатых задач.

## Риски

Локально успешные команды могут не работать в чистом runner. Проверить отсутствие caches и независимость от домашнего окружения.

Мера снижения: выполнить относящиеся к риску сценарии и сохранить доказательства в результате; при блокере не ставить `выполнена`.
