## Цель

Довести новый command API до полного ролевого жизненного цикла с атомарностью и точной окончательной валидацией.

## Ожидаемый результат

Save/submit/confirm/return по новому DTO и новая матрица интеграционных тестов команд.

## Объём работ

1. Разделить parsing/validation/domain command/storage по принятой архитектуре. Проверить revision, статус, собственность отчёта, принадлежность назначений и их учебный год.
2. Реализовать save draft и submit как атомарную запись всего содержимого; rule пустоты брать из Task 03, разрешать только замены без назначений.
3. Реализовать добавление/редактирование/удаление замен по ID: точные часы, date-only календарно существующая и внутри месяца, одно description, отсутствие чужих/дублирующихся ID.
4. Confirm/return принимать только от завуча для submitted; нельзя редактировать часы этими командами. Сервер назначает время и подтверждающего, confirmed неизменяем для обеих ролей.
5. Проводить точную нормализацию часов, пустое=0, отрицательные/невалидные →422, значения выше 999 разрешены. Не доверять status/totals/teacher/confirmation из тела.
6. Передавать CAS внутрь Task 10; тестировать конкурентные save/submit/confirm/return и согласованность ответа своей записи. Не повторять автоматически неизвестно завершившийся submit без нового чтения.

## Что не входит в задачу

История, причины возврата, массовое подтверждение, автослияние и UI.

Общие исключения продукта: комментарии/история, экспорт/печать, массовое подтверждение, клиентская админка и офлайн-синхронизация.

## Функциональные требования

- Учитель проходит save → submit → return → edit → submit → confirm; после confirm обе роли получают отказ на изменения.
- Неверная дата, чужое назначение/замена, неправильная роль и stale revision не меняют ни заголовок, ни детей.

Обязательные подробности поведения перечислены в объёме работ. Поля и DTO брать из зафиксированных контрактов.
