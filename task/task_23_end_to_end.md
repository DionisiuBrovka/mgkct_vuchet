## Цель

Доказать совместимость новой схемы, Shelf и release Web на полном пути обеих ролей и включить E2E в master-check.

## Ожидаемый результат

Изолированный browser E2E suite по Task 07, подключение к scripts/check.sh и `task/integration_qa.md` с результатами.

## Объём работ

1. Создать/подключить выбранный Task 07 browser runner, поднять временную чистую базу, реальный Shelf и release Web; подготовить только тестовые аккаунты/справочники.
2. Пройти вход/restore/logout обеих ролей; проверить блокировку и смену роли через закрытый тестовый admin-channel без передачи сервисного токена браузеру.
3. Пройти teacher: месяцы → дробные часы → add/edit/delete same-day substitutions → save → submit; admin: поиск+статус → review → return → повторная отправка → confirm → readonly.
4. Отдельно проверить no assignments/substitutions-only, ошибку 422/сеть с сохранением текста и конфликт двух сессий без auto-merge, точные дроби/большие суммы.
5. На уровне прямого HTTP проверить матрицу прав и запрет raw PB, атомарность/конкурентность, календарь включая август; не дублировать всю таблицу unit cases в браузере.
6. Подключить необходимые E2E к полному scripts/check.sh, выполнить весь мастер-скрипт. Исправлять только обнаруженные интеграционные дефекты, фиксируя затронутые будущие задачи.

## Что не входит в задачу

Новые функции, эксплуатационный деплой на неизвестную машину, тестирование рабочими учётными записями.

Общие исключения продукта: комментарии/история, экспорт/печать, массовое подтверждение, клиентская админка и офлайн-синхронизация.

## Затрагиваемые компоненты и файлы

- Выбранный Task 07 каталог E2E — создать тесты, не считать его заранее существующим.
- `scripts/check.sh` и helpers — подключить E2E.
- `client/`, `server/`, `data/pocketbase/` — только доказанные дефекты стыков.
- `task/integration_qa.md` — создать протокол.

Пути исходного аудита могут уточняться по результатам зависимостей. Новый путь не считать существующим до проверки; расширение объёма обосновать.

## Функциональные требования

- Реальный browser → Shelf → PB проходит полный цикл, включая возврат и confirmed, без mocks на основном пути.
- Точные значения и итоги одинаковы в форме, после reload, в API и в хранилище; публичные ответы не раскрывают секреты.

Обязательные подробности поведения перечислены в объёме работ. Поля и DTO брать из зафиксированных контрактов.

## Архитектурные ограничения

- Сохранять согласованность с результатами зависимостей и приоритетом product_spec.
- Не добавлять совместимость со старой базой/API и функции вне §20.
- Добавлять содержательные комментарии только к неочевидной логике.
- Клиент обращается только к Shelf и не знает коллекций PocketBase.
- Окончательные права, валидация, статусы и итоги принадлежат Shelf; PB обеспечивает ограничения и атомарность.
- Тестовые базы и учётные записи изолированы от рабочих данных.

## Ошибки и особые случаи

- Два окна одного учителя и два завуча; timeout после commit; block пользователя с открытой страницей.
- Август, граница года, no assignments, одинаковые имена, две одинаковые замены, недоступный PB.

## Автоматические проверки

Все команды выполняются из корня репозитория. Окружение должно соответствовать согласованным версиям; тесты работают только на временных базах. `scripts/check.sh` создаётся в Task 22, после Task 23 полный запуск включает E2E; `scripts/deploy.sh` и его изолированный `--self-test` создаются в Task 25. Это целевые команды зависимостей, а не существовавшие при аудите файлы.

```bash
bash scripts/check.sh
git diff --check
```

Если команда или путь изменены выполненной зависимостью, сначала зафиксировать актуальную замену и причину, затем выполнить её. Ошибка окружения и пропуск обязательной проверки не означают успешную приёмку.

## Ручная проверка

Дополнительно пройти основной цикл вручную на release Web, сравнить отображаемые суммы и проверить reload/logout; отделить ручные результаты от автоматических.

Ожидаемый результат — критерии приёмки выше. Записать фактическую среду, шаги и наблюдения; ручную проверку не подменять наличием теста.
