## Q1 — Август и доступные периоды

**Почему важно.** §8 явно оставляет август на проектирование. Учитель не выбирает учебный год; приложение должно согласованно вести себя на 31 июля/1 августа и 31 августа/1 сентября. Доступ по старой прямой ссылке и период завуча тоже должны иметь явную политику.

**Доказательство исходного состояния.** `client/lib/core/constants.dart:currentAcademicYear` считает август частью прежнего учебного года, а `AdminHomeScreen._monthNumToRu` выбирает сентябрь. Сервер `ReportService.period/statuses` принимает переданный год, не определяет текущий.

**Варианты.**
- До 31 августа включительно показывать завершившийся учебный год сентября–июля; август не является отчётным месяцем.
- В августе показывать будущий учебный год.
- В августе показывать отдельное состояние без редактирования отчётов.

**Рекомендация.** Первый вариант сохраняет возможность завершить июльский отчёт и не создаёт двенадцатого месяца. Для учителя показывать все 11 месяцев автоматически выбранного года; старую ссылку после смены года отклонять с переходом к актуальному списку. Для завуча сохранить выбор года/месяца, включая существующие прошлые отчёты. Подтвердить эти границы вместе с августом. Часовую зону Europe/Minsk зафиксировать как техническое допущение.

**Затрагивает.** Серверную календарную политику, периоды API, assignments.academic year, оба списка месяцев, доступ по прямым ссылкам, calendar/E2E tests.

**Заблокированы.** Непосредственно [03](task_03_period_and_report_policy.md); через неё [05](task_05_schema_design.md), затем новый API [06](task_06_api_contract.md) и все задачи, зависящие от него. [01](task_01_architecture.md), [02](task_02_decimal_contract.md), [04](task_04_session_design.md) могут продвигаться независимо в рамках собственных условий.

## Q2 — Что считается полностью пустым отчётом

**Почему важно.** §11.2 запрещает отправку полностью пустого отчёта, но §11.4 допускает пустое поле как ноль. Автоматически подставленные назначения образуют строки без фактически проведённых часов.

**Доказательство.** `ReportService.change` запрещает submit только при `entries.isEmpty && substitutions.isEmpty`. Тест `academic year excludes January from previous academic year` отправляет отчёт с нулевой строкой.

**Варианты.**
- Отправлять можно, только если точный общий итог положителен; пустой/нулевой черновик сохранять можно.
- Достаточно существования строки или замены, даже если все часы нулевые.
- Разрешить отдельное подтверждённое пользователем нулевое сообщение. Это расширяет текущий UX и потребует отдельного согласования, не включено в план.

**Рекомендация.** Первый вариант: «пустой» означает отсутствие проведённых часов. Отчёт только с заменами с положительными часами остаётся допустимым. Нулевое поле не является ошибкой само по себе. Подтвердить также, можно ли оставлять нулевую замену среди других положительных строк; рекомендуемо разрешить, если её дата/описание валидны.

**Затрагивает.** Серверную submit-валидацию, подсказки UI, схемные required/default для нулей, тестовые фикстуры.

**Заблокированы.** Непосредственно [03](task_03_period_and_report_policy.md); затем [05](task_05_schema_design.md), [06](task_06_api_contract.md), [13](task_13_server_report_commands.md), [17](task_17_teacher_report_editor.md), [18](task_18_teacher_substitutions.md), [23](task_23_end_to_end.md), [28](task_28_final_acceptance.md) и их зависимые этапы.

## Q3 — Изменение справочников и назначений, используемых отчётом

**Почему важно.** §13 требует правил удаления и ссылочной целостности; §11 запрещает изменение confirmed через приложение. Названия сейчас читаются из живого назначения: переименование справочника или замена его связи могут изменить вид принятого отчёта без новой revision.

**Доказательство.** `ReportService.report` получает subject/group из expanded assignment; draft дополняется текущими assignments. Исходные миграции не описывают фиксацию названий для принятого отчёта.

**Варианты.**
- Запрещать удаление и изменение значимых полей используемых назначений/справочников; для нового назначения создавать новую запись.
- Фиксировать названия/данные назначения в snapshot строки отчёта, сохраняя нормализованные связи.
- Всегда показывать текущие названия, явно считая изменения справочников допустимыми исправлениями отображения.

**Рекомендация.** Первый вариант как самый простой для локальной системы без истории. Описать точную границу ограничения для draft/submitted/confirmed; новые назначения в draft можно подхватывать при явной загрузке, изменение состава между чтением и сохранением требует понятного отказа/перезагрузки. Если колледжу важно свободное переименование справочников, выбрать snapshot-вариант. Историю проверок или версий не добавлять.

**Затрагивает.** Схему связей/полей и hooks целостности для PB-админки, GET/POST отчёта, CAS при изменении назначений, отображение confirmed и тесты удаления.

**Заблокированы.** Непосредственно [03](task_03_period_and_report_policy.md), далее [05](task_05_schema_design.md), [06](task_06_api_contract.md), [09](task_09_clean_schema.md), [10](task_10_atomic_report_storage.md), [12](task_12_server_report_queries.md), [13](task_13_server_report_commands.md), [17](task_17_teacher_report_editor.md), [20](task_20_admin_report_review.md) и общая приёмка. Окончательный data contract без ответа не фиксировать.

## Q4 — Transport сохраняемой сессии в локальной сети

**Почему важно.** Требуется сохраняемый вход и блокировка старой сессии, но целевое HTTP/HTTPS-развёртывание ещё не определено. От этого зависят cookie flags, browser storage, CORS и CSRF. Нельзя проектировать механизм, работающий только на localhost.

**Доказательство.** Compose публикует приложение по HTTP на 8090; TLS-компонента в конфигурации нет. `DEPLOY.md` только предлагает внешний HTTPS-прокси. `ApiService` хранит bearer в памяти.

**Варианты.**
- HTTPS в LAN через подготовленный прокси/сертификат; сессия в защищённой HttpOnly-cookie.
- Простой HTTP в изолированной LAN как разрешённая продуктом среда; выбрать и явно описать совместимый механизм сессии и его ограничения, без неработающего Secure-cookie.
- Поддерживать оба режима с явной конфигурацией; дороже по реализации и проверкам.

**Рекомендация.** Если HTTPS уже подготовлен или владелец готов его обеспечить, первый вариант. Иначе проектировать простой HTTP LAN-режим явно, не добавляя инфраструктуру молча. Выбор собственного session registry или пользовательского PB-токена, срок жизни, отзыв и активность — инженерный результат Task 04 после определения среды, не отдельная обязанность владельца выбирать библиотеку.

**Затрагивает.** Auth/session contract, возможную коллекцию сессий, middleware и клиентский restore, deploy/CI browser-стенд и .env.example.

**Заблокированы.** Непосредственно [04](task_04_session_design.md); затем [05](task_05_schema_design.md), [06](task_06_api_contract.md), [08](task_08_runtime_design.md), [09](task_09_clean_schema.md), [11](task_11_server_auth_and_http.md), [14](task_14_client_foundation.md), [15](task_15_client_session_and_login.md), [25](task_25_containers_and_deploy.md), [26](task_26_continuous_integration.md), [28](task_28_final_acceptance.md) и их потомки. [01](task_01_architecture.md), [02](task_02_decimal_contract.md), [03](task_03_period_and_report_policy.md) могут выполняться по своим условиям.
