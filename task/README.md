# Набор задач большого рефакторинга «Вычитки»

Подготовлено 2026-09-07 по [основному заданию](main_task.md), [спецификации](product_spec.md) и [шаблону](task_template.md). **28 задач, 8 волн.** В этой сессии выполнены исследование и декомпозиция; сам рефакторинг не начат. Статус «не начата» не означает, что задача уже готова к исполнению.

В исходных документах встречается `main_tasks.md`, но фактический файл называется `main_task.md`. Он сохранён без переименования и дублирования; product_spec и task_template тоже не изменялись. Созданные документы ссылаются на фактический путь.

## Как запустить задачу

Открой новую сессию в корне этого репозитория и передай: «Выполни задачу `task/task_NN_short_name.md` по её инструкциям. Сначала проверь условия начала и результаты зависимостей». Выбирай реальное имя по ссылке в таблице. Не проси повторно декомпозировать уже готовую задачу.

До изменений исполнитель читает текущую задачу, этот индекс, product_spec, актуальный AGENTS при наличии и фактические результаты зависимостей. Выполняет только выбранную задачу, запускает проверки, просматривает diff, очищает свои временные артефакты и обновляет статус **в обоих местах** вместе с фактическим результатом. Новые вопросы/отклонения переносит в ещё не начатые зависимые задачи. Для проектных задач реализация результата означает законченный нормативный документ, а не исходный код.

Легенда: `не начата` — работа не выполнялась; `в работе` — начата в своей сессии; `заблокирована` — записан конкретный препятствующий вопрос/сбой; `выполнена` — критерии и необходимые проверки подтверждены. Не закрывать задачу по одному факту создания файлов.

## Решения и критический порядок

Открытые вопросы: [open_questions.md](open_questions.md). Q1 — август/доступные периоды; Q2 — нулевой отчёт; Q3 — изменения используемых справочников; Q4 — HTTP/HTTPS для сохраняемой сессии. Рекомендации пока не приняты владельцем.

Начать можно с [01](task_01_architecture.md). После неё независимо разрабатываются [02](task_02_decimal_contract.md), [03](task_03_period_and_report_policy.md), [04](task_04_session_design.md), но окончательная фиксация 03/04 требует ответов владельца. Схема [05](task_05_schema_design.md) объединяет эти решения, API [06](task_06_api_contract.md) фиксируется после схемы. **Клиентская реализация 14 не начинается до выполненных 06, 09 и 07**: используются стабильные DTO и реализованная схема, даже если часть серверных команд ещё разрабатывается.

Внутренний CAS [10](task_10_atomic_report_storage.md), auth/HTTP [11](task_11_server_auth_and_http.md) и клиентский фундамент [14](task_14_client_foundation.md) могут идти одновременно после собственных зависимостей. Query API [12](task_12_server_report_queries.md) и команды [13](task_13_server_report_commands.md) открывают дальнейшие UI-сценарии. Преподаватель [16](task_16_teacher_periods.md), [17](task_17_teacher_report_editor.md), [18](task_18_teacher_substitutions.md) и завуч [19](task_19_admin_overview.md), [20](task_20_admin_report_review.md) могут развиваться параллельно в разных feature. Визуальный QA [21](task_21_visual_polish.md) и master-check [22](task_22_local_check_script.md) также независимы по основным файлам. Интеграция и финальная приёмка требуют единого согласованного снимка.

Параллельность означает отсутствие логической зависимости и совместимые границы файлов, а не разрешение одновременно править общие модели, routing, pubspec/lockfiles или индекс. Для совместного файла договориться о владельце; изменения индекса/контрактов согласовывать последовательно. Номера — рекомендуемый порядок, граф задаётся колонкой «Зависимости». Волны не являются дополнительными барьерами сверх графа.

### Реальный серверный API

Источник: `server/lib/server.dart:createHandler`. Ниже только старый контракт, новый определяет Task 06.

| Метод/путь от /api | Реализация | Наблюдение |
|---|---|---|
| GET /health | store.health | Проверяет PB через сервисный клиент |
| GET /auth/users | store.list(users) | Только id/name, но name из display_name; активности нет |
| POST /auth/login | store.login | profileId/password, token/user; 20 попыток/минуту на адрес соединения |
| GET /auth/me | actor request.context | authRefresh даёт текущую роль; logout endpoint отсутствует |
| GET /teachers/:teacher/years/:year | ReportService.statuses | Учебный год приходит от клиента |
| GET /admin/months/:year/:month | ReportService.overview | Все преподаватели и статусы; фильтров API нет |
| GET /reports/:teacher/:year/:month | ReportService.report | Full snapshot, но без explicit assignment/grand totals |
| POST /reports/:teacher/:year/:month/:action | ReportService.change | save/submit/confirm/reject, revision и атомарный storage write |

Защищены все API-пути кроме health/users/login; unknown API даёт JSON 404. Ошибки содержат message, есть 400/401/403/409/413/422/429/502/504. JSON body ограничен 1 MiB. Таймаут store 15 s, client 20 s. Нет оснований объявлять авторизацию/транзакции полностью отсутствующими.

Критические отличия: `_hours` допускает num в 0–999; `_date` проверяет ДД.ММ.ГГГГ и выбранный месяц; `_text` проверяет строку group до 200 символов; `_items` ограничивает список 500 элементами. Это существующие ограничения, не автоматически принятые целевые правила. `report` складывает num, дублирует статус в entries, повторяет GET при смене ревизии существующего отчёта, но не аналогично для concurrent first create. `change` требует полный состав назначений и считает пустым только отсутствие entries/substitutions. Все эти вопросы распределены в 02/03/06/12/13.

## Правила промежуточного состояния

Новая схема несовместима со старым API/клиентом по условию продукта. Task 01 должна задать последовательное переключение и изолированные стенды: частичные результаты могут иметь собственные module/contract tests, но не считаться пригодными к deployment. Не вводить временные legacy DTO/миграции ради зелёного старого теста. При изменении схемы/DTO адаптировать тестовую фикстуру и согласовать затронутые ещё не начатые задачи.

Полный master-check появляется в Task 22 и содержит базовый интеграционный health smoke. Task 23 реализует и подключает browser E2E, после чего полный check включает их обязательно. Зависимость 23→22 исключает цикл «сначала E2E, но для него сначала ещё не существующий check». Task 25 добавляет deploy self-test на временном проекте/томе. На интеграционных и финальной задачах полный master-check обязателен.
