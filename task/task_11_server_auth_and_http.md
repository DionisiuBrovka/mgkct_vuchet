## Цель

Реализовать новый auth API, изолированный request context и единообразную обработку HTTP-ошибок на новой схеме.

## Ожидаемый результат

Выделенные HTTP/DTO/auth/storage-границы, login/directory/restore/logout/health и тесты сессий и прав.

## Объём работ

1. Разделить createHandler на маршрутизацию/middleware и сервисы по Task 01, убрать зависимость доменных DTO от RecordModel и legacy profileId. Изменять report-логику здесь только для компиляции новых границ.
2. Реализовать directory только с id/name, login выбранного ID, restore текущего пользователя и logout согласно session contract; не выдавать email/роль в публичном списке.
3. Проверять активность и актуальную роль на каждом защищённом запросе, при входе/restore; исключить общий пользовательский authStore и изолировать сервисный клиент.
4. Согласовать 401/403 и инфраструктурные ошибки: PB outage не маскировать неверным паролем; сохранить bounded timeout, безопасные логи, body limit и разумное ограничение попыток.
5. Реализовать CORS/credentials/CSRF по выбранной сессии, health с проверкой PB и JSON-ошибки для API, включая незнакомые маршруты.
6. Проверить повторный запуск Shelf и браузерный transport, revoke/block/delete/role change, одновременные запросы разных пользователей и отсутствие секретов в ответах.

Бизнес-запись отчётов Task 13, смена пароля, корпоративная авторизация, реализация клиентского хранения.

Общие исключения продукта: комментарии/история, экспорт/печать, массовое подтверждение, клиентская админка и офлайн-синхронизация.

- Вход/restore/logout работают по новому контракту, заблокированный пользователь не входит и не продолжает работу со старой сессией.

Обязательные подробности поведения перечислены в объёме работ. Поля и DTO брать из зафиксированных контрактов.
