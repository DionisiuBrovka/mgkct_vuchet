Старые данные сохранять не требуется; скрытное удаление локальной базы недопустимо. Функции вне §20 не реализовать.

Исходный аудит от 2026-09-07; это не обещание состояния после предшественников. Перед работой перепроверить пути и фактические результаты зависимостей.

- `server/lib/server.dart:createHandler` содержит текущие 7 шаблонов маршрутов с универсальным `<action>` для save/submit/confirm/reject.

## Цель

Опубликовать полный новый контракт до адаптации клиента, с типизированными примерами и матрицей прав.

## Ожидаемый результат

Создать `task/api_contract.md` и `task/api_examples.json` (новый набор несекретных DTO-примеров); это нормативные входы серверных и клиентских тестов.

## Объём работ

1. Перечислить методы/маршруты health, directory, login, me/restore, logout, teacher periods/statuses, admin overview/filter, report read, save, submit, confirm, return. Технические значения периода и полей — английские/числовые, русский текст — отображение.
2. Для каждого запроса задать роль, тело/query, ответ и ошибки, nullable/пустые значения, ID новых замен, пропущенные/неизвестные поля и все итоги. Старые profileId и legacy-форматы не поддерживать.
3. Согласовать представление пустого несохранённого отчёта и revision=0, CAS при первом создании, рост ревизии на каждой операции, статусные конфликты и отсутствие автоматического merge.
4. Отправка — одна атомарная команда с полным содержимым; confirm/return не принимают редактирование часов. Сведения подтверждения выставляет сервер.
5. Зафиксировать точные даты и часы из зависимостей, единый JSON ошибок (стабильный код, понятное message, адрес ошибок поля при необходимости), обязательные 401/403/409/422 и отдельные malformed JSON/404/413/429/502/504.
6. Описать согласованность чтения, актуальную роль/активность, публичность только трёх операций, health при недоступном PB, CORS по session contract. Определить серверную или клиентскую фильтрацию по ФИО/статусу как обратимое техническое решение с едиными тестами.

## Что не входит в задачу

Серверная реализация, клиентские запросы, версионирование старого API.

Общие исключения продукта: комментарии/история, экспорт/печать, массовое подтверждение, клиентская админка и офлайн-синхронизация.

## Затрагиваемые компоненты и файлы

Пути исходного аудита могут уточняться по результатам зависимостей. Новый путь не считать существующим до проверки; расширение объёма обосновать.

## Функциональные требования

- Любую операцию двух ролей можно воспроизвести только по контракту, без чтения PocketBase-коллекций клиентом.
- Примеры содержат черновик, submitted, confirmed, только замены, длинную дробь, пустой отчёт и 401/403/409/422.

Обязательные подробности поведения перечислены в объёме работ. Поля и DTO брать из зафиксированных контрактов.

## Архитектурные ограничения

- Сохранять согласованность с результатами зависимостей и приоритетом product_spec.
- Не добавлять совместимость со старой базой/API и функции вне §20.
- Добавлять содержательные комментарии только к неочевидной логике.
- Клиент обращается только к Shelf и не знает коллекций PocketBase.
- Окончательные права, валидация, статусы и итоги принадлежат Shelf; PB обеспечивает ограничения и атомарность.
- Тестовые базы и учётные записи изолированы от рабочих данных.

## Ошибки и особые случаи

- Две первые записи одного периода; stale revision после confirm/return; неверный формат даты/часов.
- Неверный маршрут, незнакомое действие, отсутствие teacher, недоступность PB и повреждённый JSON.

## Критерии приёмки
