# Спецификация продукта «Вычитка»

## 1. Статус документа

Этот документ является основным источником продуктовых и технических требований для новой версии приложения. Он описывает целевое поведение системы, обязательные ограничения и функции, которые не входят в текущую итерацию.

При расхождении источников используй следующий приоритет:

1. требования этого документа;
2. ограничения мастер-промпта `task/main_tasks.md`;
3. фактическое состояние кода и тестов как описание текущей реализации;
4. старые `README.md`, `DEPLOY.md`, `CLAUDE.md` и другие устаревшие документы.

Старые документы и код помогают понять исходное состояние, но не отменяют требования новой версии.

## 2. Назначение приложения

«Вычитка» — внутренняя система УО «Минский государственный колледж цифровых технологий» для ежемесячного учёта проведённых преподавателями занятий и замен.

Преподаватель заполняет месячный отчёт и отправляет его завучу. Завуч проверяет указанные часы, после чего подтверждает отчёт или возвращает его преподавателю в черновик.

Пользовательский интерфейс, ФИО, названия групп, предметов и месяцев должны отображаться на русском языке. Технические имена в коде, API и базе данных должны быть на английском языке.

## 3. Целевая среда использования

- Основная платформа — браузер.
- Приложение работает внутри локальной сети.
- Клиент должен открываться с других компьютеров локальной сети по адресу развёрнутого приложения.
- Архитектуру и безопасность не следует усложнять корпоративными механизмами, не нужными локальной системе.
- Базовые меры защиты обязательны: серверная аутентификация и авторизация, валидация данных, изоляция PocketBase и защита секретов.
- Ожидается поддержка Flutter Web. Возможность нативной Flutter-сборки не должна определять архитектуру, если это не подтверждено анализом проекта как актуальное требование.

## 4. Проблемы текущей версии

Новая версия должна устранить следующие системные проблемы:

- ответственность клиента, сервера и базы данных разделена нелогично;
- часть бизнес-логики и значимых проверок выполняется на клиенте;
- код имеет запутанные зависимости, неединообразную структуру и требует рефакторинга;
- в коде недостаточно пояснений для неочевидных бизнес-правил и архитектурных решений;
- текущая модель данных недостаточно нормализована;
- предметы и группы хранятся произвольным текстом, из-за чего опечатки нарушают целостность данных;
- для отображения ФИО создано дополнительное поле `display_name`, хотя у auth-пользователя PocketBase уже есть штатное поле имени;
- старые документы, скрипты сборки и деплоя требуют ревизии и согласования;
- интерфейс и пользовательские сценарии требуют визуальной и логической полировки.

Требование о комментариях не означает необходимость комментировать каждую строку. Добавляй комментарии и документацию только для сложной логики, бизнес-правил и неочевидных решений. Понятные имена и простая структура предпочтительнее поясняющих очевидное комментариев.

## 5. Целевая архитектура

Система должна иметь три чётко разделённые части:

```text
Flutter Web-клиент
        ↓ HTTP / JSON
    Dart Shelf API
        ↓ внутренний доступ
 PocketBase / SQLite
```

### 5.1. Клиент

Каталог `client/` отвечает за:

- экраны и компоненты интерфейса;
- навигацию;
- локальное состояние представления и пользовательского ввода;
- предварительную проверку формы для удобства пользователя;
- вызов серверного API;
- отображение загрузки, ошибок, пустых состояний и результата действий.

Клиент не должен:

- использовать PocketBase SDK;
- обращаться к PocketBase напрямую;
- знать имена коллекций и полей PocketBase;
- принимать окончательные бизнес-решения;
- быть единственным местом проверки прав или целостности данных.

### 5.2. Сервер

Каталог `server/` содержит Dart Shelf API и отвечает за:

- аутентификацию и восстановление пользовательской сессии;
- проверку роли и прав для каждого запроса;
- бизнес-логику и переходы статусов;
- окончательную валидацию входных данных;
- расчёт итогов;
- согласованный формат запросов, ответов и ошибок;
- атомарную работу с месячным отчётом;
- взаимодействие с PocketBase.

Нельзя разделять контекст пользователя между запросами. Актуальная роль и возможность входа должны проверяться сервером, а не доверяться данным клиента.

### 5.3. База данных

Каталог `data/pocketbase/` отвечает за:

- воспроизводимое создание новой схемы PocketBase;
- коллекции, связи, ограничения и индексы;
- правила прямого доступа;
- внутренний транзакционный механизм, если он необходим;
- тесты схемы и инициализации;
- средства локального запуска PocketBase.

PocketBase доступен только серверу и администратору. Обычные пользователи не должны напрямую читать или изменять прикладные коллекции.

### 5.4. Технологический стек

Исходный стек, который следует сохранить, если анализ не выявит обоснованной необходимости изменения:

- клиент: Flutter, Cubit или `flutter_bloc`, Freezed, `go_router`, `get_it`, HTTP;
- сервер: Dart, Shelf, `shelf_router`, `shelf_static`, PocketBase SDK;
- данные: PocketBase 0.40.1 и SQLite;
- развёртывание: контейнеры для приложения и хранилища; Shelf может раздавать собранный Flutter Web.

Не заменяй технологии только ради новизны. Любая замена должна иметь явную пользу, учитывать стоимость перехода и упрощать либо существенно улучшать локальную эксплуатацию.

## 6. Пользователи и аутентификация

В системе две роли:

- `teacher` — преподаватель;
- `admin` — завуч.

### 6.1. Вход

Пользователь не вводит логин вручную:

1. клиент получает с сервера публичный список пользователей;
2. пользователь выбирает себя из списка;
3. пользователь вводит пароль;
4. сервер проверяет выбранную учётную запись и пароль;
5. сервер возвращает сессию и роль;
6. клиент открывает интерфейс соответствующей роли.

Публичный список входа содержит только ID и ФИО. Email и роль публично не выдаются. Пользователи с одинаковым ФИО различаются по ID.

Для ФИО необходимо использовать штатное поле имени auth-коллекции PocketBase. Дополнительное поле `display_name` создавать нельзя; администратор не должен вводить одно имя дважды. Точное техническое имя штатного поля следует подтвердить по используемой версии и схеме PocketBase.

### 6.2. Сессия

- Успешный вход сохраняется после перезагрузки страницы или перезапуска клиента.
- При запуске клиент восстанавливает сохранённую сессию и проверяет её через сервер.
- В интерфейсе должна быть возможность выхода.
- Истёкшая, отозванная или заблокированная сессия требует повторного входа.
- Пароли, сервисные токены и секреты PocketBase нельзя хранить в клиенте.
- Смена и восстановление пароля через клиент не требуются.
- Пользователей, их пароли и состояние активности администратор управляет через PocketBase.
- Заблокированный пользователь не может войти или продолжить работу со старой сессией.

Экран входа должен понятно обрабатывать неверный пароль, недоступность сервера, отсутствие пользователей и ошибку загрузки списка.

## 7. Роли и права

| Операция | Преподаватель | Завуч |
|---|---|---|
| Просмотр отчётов | Только собственные | Все преподаватели |
| Изменение часов и замен | Только собственный черновик | Нет |
| Сохранение и отправка | Только собственный черновик | Нет |
| Подтверждение или возврат | Нет | Только отчёт на проверке |
| Изменение подтверждённого отчёта | Нет | Нет |

Клиент скрывает недоступные элементы, но окончательную проверку прав выполняет сервер. Запрещённое действие должно оставаться невозможным при прямом HTTP-запросе.

Сервисная учётная запись PocketBase используется только сервером. Её пароль и токен никогда не передаются клиенту.

## 8. Учебный год и выбор периода

- Учебный год длится с сентября по июль.
- Преподаватель не выбирает учебный год вручную.
- Приложение автоматически определяет текущий учебный год по текущей дате.
- Преподаватель выбирает месяц внутри автоматически выбранного учебного года.
- Правило должно корректно работать на границе календарных лет.
- Поведение приложения в августе необходимо определить на этапе проектирования и явно зафиксировать до реализации.
- Отчёт однозначно определяется пользователем, календарным месяцем и календарным годом.

## 9. Сценарий преподавателя

Преподаватель должен иметь возможность:

1. войти в систему;
2. увидеть месяцы текущего учебного года и статусы своих отчётов;
3. выбрать доступный месяц;
4. увидеть назначенные ему предметы и группы;
5. заполнить дробные значения часов по видам нагрузки;
6. добавить, отредактировать и удалить замены;
7. увидеть итоги до сохранения и отправки;
8. сохранить черновик;
9. отправить отчёт на проверку;
10. после возврата снова отредактировать и отправить отчёт;
11. просмотреть подтверждённый отчёт без возможности изменения;
12. выйти из системы.

Если назначений нет, форма часов не показывается. Пользователь видит понятное сообщение о том, что часы не назначены и необходимо обратиться к администратору.

Копирование значений из предыдущего месяца не требуется.

## 10. Сценарий завуча

Завуч должен иметь возможность:

1. войти в отдельный ролевой интерфейс;
2. выбрать период для проверки;
3. увидеть преподавателей и статусы их отчётов;
4. найти или отфильтровать преподавателя как минимум по ФИО и статусу отчёта;
5. открыть отправленный или подтверждённый отчёт;
6. увидеть предметы, группы, все виды нагрузки, замены и итоги;
7. подтвердить отчёт на проверке;
8. вернуть отчёт на проверке в черновик;
9. выйти из системы.

Причина возврата, комментарии и история проверок не нужны. Не требуются массовое подтверждение, печать, экспорт и аналитическая сводка за месяц.

## 11. Месячный отчёт

### 11.1. Жизненный цикл

```text
draft → submitted → confirmed
           ↓
         draft
```

- Преподаватель редактирует только `draft`.
- Отправка атомарно сохраняет данные и переводит `draft` в `submitted`.
- Завуч подтверждает `submitted`, переводя его в `confirmed`.
- Завуч возвращает `submitted` в `draft`.
- `confirmed` нельзя редактировать ни одной ролью.
- Статус хранится на уровне отчёта и является единственным источником истины.

### 11.2. Содержимое

Отчёт содержит:

- строки часов по учебным назначениям;
- список замен;
- серверные итоги по видам нагрузки;
- итог по назначениям;
- итог замен;
- общий итог;
- текущий статус и ревизию.

Отчёт только с заменами допустим. Полностью пустой отчёт отправлять нельзя.

### 11.3. Виды нагрузки

| Поле API | Поле PocketBase | Название в интерфейсе |
|---|---|---|
| `lectureHours` | `lecture_hours` | Лекции |
| `practicalHours` | `practical_hours` | Лабораторные и практические занятия |
| `courseProjectHours` | `course_project_hours` | Курсовые проекты |
| `consultationHours` | `consultation_hours` | Консультации |
| `additionalAssessmentHours` | `additional_assessment_hours` | Дополнительный контроль |
| `examHours` | `exam_hours` | Экзамены и дифференцированные зачёты |

### 11.4. Правила часов

- Часы могут быть дробными.
- Дробная часть сохраняется и отображается без округления или потери значения.
- Пустое значение эквивалентно нулю.
- Отрицательные и некорректные значения запрещены.
- Максимальный предметный итог не ограничивается.
- Старый верхний предел `999` применять нельзя.
- Ввод десятичного значения должен быть удобен для русскоязычного пользователя и однозначно нормализоваться сервером.
- Клиент может заранее подсветить ошибку, но окончательную проверку выполняет сервер.

### 11.5. Конкурентное редактирование

- Каждое сохранение передаёт `revision`.
- Устаревшая версия получает HTTP 409.
- После конфликта пользователь заново открывает актуальный отчёт.
- Автоматическое слияние не требуется.
- Отчёт, строки и замены сохраняются атомарно.
- При ошибке сети, валидации или конфликте введённые данные остаются в форме.

## 12. Замены

Каждая замена имеет собственный ID и содержит:

- количество заменённых часов;
- дату замены;
- одно свободное текстовое описание того, кого заменяли и в какой группе.

Дата вводится через удобный контрол выбора или ввода даты. Сервер проверяет календарную корректность даты и её принадлежность выбранному месяцу отчёта.

Описание намеренно остаётся одним текстовым полем. Для замены не нужно создавать отдельные связи с пользователем и группой. Удаление должно затрагивать только выбранную по ID замену.

## 13. Целевая модель данных

Новая схема должна содержать отдельные сущности или коллекции как минимум для:

| Сущность | Назначение |
|---|---|
| `users` | Auth-пользователи PocketBase, штатное имя и роль |
| `subjects` | Единый справочник предметов |
| `groups` | Единый справочник учебных групп |
| `assignments` | Связь преподавателя, предмета, группы и учебного года |
| `teaching_reports` | Период, преподаватель, статус, ревизия и сведения о подтверждении |
| `teaching_report_entries` | Строка отчёта, назначение и виды часов |
| `substitutions` | Замена с собственным ID и связью с отчётом |

`assignments` должен ссылаться на пользователя, предмет и группу, а не хранить названия произвольным текстом.

Необходимо определить и проверить:

- уникальность названий предметов и групп с подходящей нормализацией;
- уникальность назначения в пределах преподавателя, предмета, группы и учебного года;
- уникальность периода «преподаватель + месяц + календарный год»;
- уникальность пары «отчёт + назначение»;
- обязательность полей;
- индексы;
- правила удаления и ссылочную целостность;
- запрет прямого пользовательского доступа;
- атомарное сохранение агрегата отчёта.

Статус не следует дублировать в строках отчёта без новой обоснованной причины.

Управление пользователями, предметами, группами и назначениями пока выполняется через закрытую административную панель PocketBase. Отдельный клиентский интерфейс администрирования не входит в эту версию.

## 14. Стратегия перехода и данных

- Проект ещё не введён в эксплуатацию.
- Существующие данные сохранять не требуется.
- Старую локальную базу можно удалить и заполнить заново.
- Не нужны перенос, резервный архив, обратная совместимость или откат старых пользовательских данных.
- Новая схема должна воспроизводимо создаваться на чистом экземпляре PocketBase.
- Удаление базы разработки не должно происходить скрытно; действие должно быть явно ограничено безопасным путём и описано.
- Совместимость со старым API и его версионирование не нужны.
- Новый API необходимо спроектировать и описать до адаптации клиента.

## 15. Требования к API

Все прикладные операции выполняются через Shelf API. Кроме получения списка входа, входа и health-check, маршруты требуют действующую сессию.

Новый API может отличаться от старого, но должен покрывать:

- health-check API и PocketBase;
- безопасный список пользователей для входа;
- вход, восстановление текущего пользователя и выход;
- статусы месяцев преподавателя;
- список преподавателей и статусов для завуча;
- получение полного отчёта;
- сохранение черновика;
- атомарное сохранение и отправку;
- подтверждение;
- возврат в черновик.

Новый контракт должен определить DTO, маршруты, методы, авторизацию, форматы дат и дробных часов, ответы, ошибки и правила конкурентности.

Ошибки возвращаются в едином JSON-формате с понятным сообщением. Как минимум различаются:

- 401 — требуется вход или сессия недействительна;
- 403 — недостаточно прав;
- 409 — конфликт ревизии или статуса;
- 422 — некорректные данные.

## 16. Интерфейс и визуальный стиль

Новая версия сохраняет узнаваемую светло-голубую палитру и декоративные облака на фоне. Полная смена визуальной концепции не требуется, но интерфейс должен стать единообразным, аккуратным и понятным.

Обязательные требования:

- основной синий цвет используется последовательно, включая `AppBar`;
- на экранах входа, выбора месяца, заполнения и проверки есть пояснение следующего действия;
- подсказки учитывают статус отчёта;
- сокращения видов часов можно раскрыть или понять непосредственно в форме;
- статусы и значки имеют всплывающие пояснения;
- на узких экранах поля часов располагаются удобно, при необходимости в два ряда;
- загрузка, отсутствие данных, ошибки и успешные действия имеют явную обратную связь;
- форма не теряет введённые данные после ошибки;
- элементы недоступных действий не вводят пользователя в заблуждение;
- экран завуча отображает назначения карточками с предметом, группой, полными названиями нагрузки и итогом;
- нулевые значения на экране проверки визуально приглушены;
- итоги назначений отделены от часов замен;
- интерфейс проверяется в браузере на целевых размерах окна.

## 17. Репозиторий и документация

Репозиторий необходимо очистить от подтверждённо устаревших, дублирующихся, временных и сгенерированных файлов. Нельзя удалять неизвестный файл без проверки его использования.

Необходимо проверить `.gitignore`, `.dockerignore`, Docker-файлы, Compose, скрипты, конфигурации CI и случайно отслеживаемые локальные данные или секреты.

После рефакторинга основная документация в корне состоит из:

- `README.md` — описание продукта, архитектуры, настройки, запуска, проверки, деплоя и типичных проблем;
- `AGENTS.md` — короткая карта репозитория и устойчивые правила работы агента.

Полезная информация из старых `DEPLOY.md`, `CLAUDE.md` и других документов переносится в новый `README.md` или `AGENTS.md`, после чего устаревшие дубли удаляются. Задачи в `task/` являются временным рабочим комплектом и исключением из правила о двух корневых Markdown-файлах.

`AGENTS.md` не должен становиться энциклопедией. Он содержит карту архитектуры, команды проверки, правила схемы и API, требования к качеству и ссылки на актуальные источники.

## 18. DevOps, CI/CD и запуск

Необходимо заново проверить и при необходимости переписать `build.sh`, `entrypoint.sh`, Docker-файлы, Compose и CI/CD-конфигурации.

### 18.1. Локальный мастер-скрипт

Один скрипт, например `scripts/check.sh`, запускается из корня и выполняет согласованный набор проверок:

- проверку инструментов;
- проверку форматирования;
- статический анализ;
- миграционные тесты;
- серверные тесты;
- клиентские тесты;
- сборку сервера;
- release-сборку Flutter Web;
- необходимую интеграционную проверку и health-check;
- понятную сводку и ненулевой код при ошибке.

Повторный запуск безопасен, скрипт не содержит секретов и не зависит от неописанного ручного состояния.

### 18.2. Мастер-скрипт деплоя

Один скрипт, например `scripts/deploy.sh`, является документированной точкой входа для развёртывания на подготовленной машине. Он:

- проверяет зависимости, конфигурацию и переменные окружения;
- не выводит секреты;
- использует однозначные версии артефактов;
- создаёт чистую схему или применяет миграции новой версии;
- поднимает клиент, Shelf и PocketBase;
- учитывает постоянный каталог данных;
- ожидает готовности и выполняет health-check;
- безопасен при повторном запуске;
- не удаляет данные без явного ограниченного режима;
- документирует первый запуск, обновление, остановку и просмотр журналов.

Деплой учитывает сетевой интерфейс, адрес Shelf API, CORS, доступ из локальной сети и недоступность PocketBase обычным клиентам.

### 18.3. CI/CD

CI использует те же команды, что и локальный мастер-скрипт, и проверяет форматирование, анализ, миграции, тесты и release-сборку. Версии Dart, Flutter и PocketBase должны быть воспроизводимыми.

Автоматический удалённый CD не требуется, пока не определены целевая машина и инфраструктура. Должны быть подготовлены проверяемые артефакты и ручной запуск мастер-скрипта деплоя. Нельзя придумывать адреса или учётные данные.

## 19. Проверки качества

Существующие проверки следует сохранить или заменить более актуальными:

```bash
python3 -m unittest discover -s data/pocketbase/tests -v
```

```bash
cd server
dart test
dart analyze
dart compile exe bin/server.dart -o build/server
```

```bash
cd client
flutter test
flutter analyze
flutter build web --release
```

Серверные и интеграционные тесты должны проверять роли, запрет прямого доступа, сохранение, переходы статусов, валидацию, дробные часы, конкурентные запросы, учебный год и восстановление сессии.

Клиентские тесты должны проверять вход, маршрутизацию ролей, сохранность ввода при ошибке, единый запрос отправки, пустое состояние без назначений, фильтрацию преподавателей и просмотр подтверждённого отчёта.

Миграционные тесты используют временные базы и не затрагивают локальные рабочие данные.

## 20. Функции вне текущего объёма

В эту версию не входят:

- комментарии и причины возврата;
- история проверок и история версий;
- месячные аналитические сводки;
- массовое подтверждение;
- печать и экспорт;
- копирование данных прошлого месяца;
- офлайн-синхронизация;
- клиентская админка пользователей, предметов, групп и назначений;
- смена и восстановление пароля;
- поддержка старой базы и старого API.

Эти возможности можно кратко отметить как дальнейшее развитие, но нельзя включать в текущий объём реализации.

## 21. Общий критерий готовности продукта

Рефакторинг завершён, когда:

- чистая база PocketBase воспроизводимо создаётся с новой схемой;
- предметы и группы представлены отдельными справочниками;
- назначения ссылаются на пользователя, предмет и группу;
- ФИО не требуется вводить дважды;
- клиент не обращается к PocketBase напрямую;
- сервер выполняет бизнес-логику, права и окончательную валидацию;
- новый API документирован и согласован с клиентом;
- работают вход, восстановление сессии и выход;
- преподаватель полностью проходит сценарий заполнения и отправки;
- завуч выполняет поиск, просмотр, подтверждение и возврат;
- дробные часы проходят через UI, API и хранилище без округления;
- права невозможно обойти прямым запросом;
- Web-интерфейс сохраняет голубую стилистику и работает в локальной сети;
- актуальные тесты, анализ и release-сборки проходят;
- локальный мастер-скрипт выполняет все проверки;
- CI выполняет тот же согласованный набор проверок;
- мастер-скрипт деплоя воспроизводимо поднимает приложение и проверяет health-check;
- репозиторий очищен;
- `README.md`, `AGENTS.md`, `.env.example` и скрипты соответствуют реализации;
- проект запускается с чистого окружения по документации.
